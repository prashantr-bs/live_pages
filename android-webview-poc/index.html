Android: making the rules check WebView content

On Android the scanner already sees web content (Chrome's WebView hands buttons, links, fields and text to accessibility services), but the rule engine skipped almost all of it. A change to the on-device rule engine alone (no capture change) takes the Angular Rule Lab from 6 to 42 of 127 known issues found, plus 36 sent to review, with 0 false alarms on the passing examples.

How this was measured. The same Angular + Ionic Rule Lab (41 rule pages, 127 deliberately broken examples) was scanned with BS talkback on a Xiaomi 22021211RI (Android 14, WebView 152) on 1 Oct. The captured snapshots were then replayed through the rule engine on a laptop (a JVM unit test, BSSnapshotReplayTest), once with the stock engine and once with the POC, and every result was scored against the known answer. Replaying stock main reproduces the device's own results exactly (6 found, 10 review), so the replay is a faithful stand-in for a device scan of the engine. The Chromium behaviour below was re-checked live on the same phone on WebView 153 today.

The Android POC's 26 "native parity" cases are issues the Android rule would also miss in a native app (for example the overlap rule only flags identical bounds, and three rules never fail by design). They are rule gaps, not WebView gaps, and are listed per rule below.

Why Android lost web content, and what the POC changes

Before

  • Chromium exposes the DOM as virtual nodes, and capture serialises them (3,884 web nodes across the Rule Lab scans).
  • Chromium never sets importantForAccessibility on them, and ~25 of 41 rules gate on that flag, so the engine skipped them.
  • Chromium sends no text size (ExtraRenderingInfo is null), so size rules never ran.
  • Several rules key on native signals that web nodes never carry (a contentDescription-only name, the focus caption, a non-android.* class).

After (rule engine only)

  • A web node the framework hands to TalkBack (isInScreenReaderTree, already captured) is treated as important, which is exactly what stock TalkBack does.
  • Every web arm keys on a new isWebViewElement flag, so native results cannot change (verified, below).
  • Web-aware arms in 17 rules (files listed at the end): role-less clickables, OCR-visible labels, line-box text size, on-screen ellipsis, icon buttons, DOM reading order.
  • Refinements that keep false alarms at zero: Ionic wrappers, layout boxes, photos, text under a sticky header, unnamed form controls.

What is supported, and what isn't

Works on web content with the POC

  • Names & labels: unnamed buttons, links, images and switches; capitalisation, duplicates, special characters, link purpose; label-in-name and label-at-front (the visible label read by OCR when an aria-label replaced it).
  • Interaction: role-less clickables (<div (click)>, invalid roles), missing role word in speech, keyboard reachability.
  • Visual: text contrast (now able to FAIL), icon-button contrast, readable text size, on-screen truncation, touch target size and spacing, 2-D scrolling.
  • AI checks now receive web elements: headings, image descriptions, images of text, reading order (in DOM order) and visual order.

Not possible or not done

  • Names from <label> / aria-labelledby: Chromium does not put them on the node (below). Unnamed form controls go to review instead of FAIL.
  • Not exposed by Chromium (14): aria-hidden / presentational elements (absent from the tree), computed CSS spacing, text scaling, key handlers, hard clips without an ellipsis.
  • Native parity (26): rule limits that apply to native apps too.
  • Fixable, not done (3): a fixed-width card overflow, placeholder contrast (needs a capture change), small ion-button touch target.
  • Out of scope, as on iOS: Chrome Custom Tabs, <canvas> UIs, cross-origin iframes.

The one real Android gap: names that come from a label

A checkbox written as <label><input type=checkbox> Accept terms</label>, or a field with <label for> / aria-labelledby, has the right name in Blink. On Android that name is nowhere on the node.

Names from aria-label, from the element's own text, or from a placeholder do arrive (in text, contentDescription or hint). So the POC cannot tell "no label" from "a label Chromium didn't pass on", and sends unnamed web form controls to review instead of FAIL (14 of the 127). The AI step sees the screenshot, so it can tell. Failing them would have produced 5 false alarms on correctly labelled fields. Still to confirm: what TalkBack actually speaks on these fields. If it says only "Tick box", users really do lose the label and these become genuine Android findings.

False alarms: what was found and fixed

The TC scorer only sees the test-case rectangles, so every failing web element in all 70 scans (529 at first) was also listed, grouped by rule and element, and each group checked against the Rule Lab template and screenshot (the iOS method). Sources found along the way, all fixed:

Remaining web fails outside the test cases (9) were checked one by one: the Rule Lab's own 11px chips (readable size, genuine), and controls scrolled under the header (still the same undersized/lowercase controls). One finding outside the test cases is a true positive the test plan didn't anticipate: ion-title really does ellipsize long page titles.

Safety checks

  • Native results unchanged: 25 other Android snapshots (production snapshots from earlier investigations) replayed with the web arms off and on. Zero changes on native elements. The only differences are web elements in the one hybrid snapshot.
  • Unit tests: all 249 existing rule-engine tests pass.
  • Kill-switch: every web arm is behind BSWebContent.enabled; off reproduces today's engine exactly (that is how the before/after replays were run).
  • Latency: rule evaluation per Rule Lab scan went from a 3.5 ms to a 7 ms median on the laptop JVM, which is the cost of actually evaluating ~50 more web elements per screen. No capture work was added. On-device timing is still to be measured.

Code

Branch prashantr/webview-android-poc in browserstack/talkback (local, not pushed). All changes are in talkback-rule-engine:

  • BSWebContent.kt (new): switch, line-box text size, WebView host helpers, Ionic control parts, label-name gap.
  • BSViewAdapter.kt: sets isWebViewElement; screen-reader-tree web nodes count as important; line box.
  • BSShouldFocusView.kt: web layout boxes are not focus stops.
  • BSRuleSupport.kt: Chromium's android.widget.Image maps to image roles.
  • BSRules.kt: text contrast (OCR guard), non-text contrast (icon buttons, photo cap), truncation (on-screen ellipsis), touch target (control parts).
  • BSAdditionalRules.kt: unsupported type, missing view type, keyboard focus, readable size, label-at-front / label-in-name (OCR label), touch spacing, label-gap review.
  • BSAIRules.kt: unnamed web controls, label-gap review, reading order in DOM order.
  • BSSnapshotReplayTest.kt (new, opt-in): replays captured snapshots through the engine.
