Text Magnification & Text Truncation — what changed, and how to read the new verdicts

iOS App Accessibility · font-magnification-support & text-truncation · WCAG 1.4.4 (text must be resizable to 200% without losing content) · deep-dive on the underlying signal problem: one signal, two truths

1 · The problem, in one picture

Both rules leaned on a single captured field that was supposed to say "this font can't scale" — but the way it was computed made one entry appear for every font in every app:

flowchart LR
  A["Any font, any app"] --> B["ask the scaling calculator:
'would the size change at each setting?'"]
  B --> C["at the DEFAULT setting the answer is
always 'no change' — by definition"]
  C --> D["'unsupported size' recorded
for 408 of 408 fonts"]
  D --> E["Text Magnification fails almost any text
Text Truncation flags almost any bounded label"]
  style D fill:#ffd7d4
  style E fill:#ffd7d4
Vendor adjudication of two eval sets put numbers on it: 39 of 39 Text Truncation findings were false positives (zero true ones existed), and 15 of 36 Text Magnification findings were false — with the true and false ones carrying byte-identical evidence, so no simple filter could separate them.

2 · Inside the old flow — one loop, three wrong answers

The production check ran the loop below for every text element. The scaling math itself was correct — the three failures are in what the loop never asked:

flowchart TD
  A["Text element captured"] --> B["take its font"]
  B --> LOOP["for EVERY size setting — all 12,
xSmall … AX3, below the default included"]
  LOOP --> CALC["ask the scaling calculator:
'what size would this font be there?'"]
  CALC --> EQ{"computed size ==
current size?"}
  EQ -- "different" --> SUP["setting recorded as supported"]
  EQ -- "same" --> UNSUP["setting recorded as UNSUPPORTED"]
  SUP --> V["rule verdict built from the list"]
  UNSUP --> V
  UNSUP -.-> R1["① at the DEFAULT setting the two sizes are equal
BY DEFINITION → one 'unsupported' entry for every
font in every app — the constant artifact"]
  SUP -.-> R2["② plain fixed font: the calculator happily computes
bigger numbers → 'supported' — but the label NEVER
re-renders, because the opt-in flag and the font's origin
are never checked. Real violations reported as fine"]
  UNSUP -.-> R3["③ correctly-built Dynamic Type font (UIFontMetrics):
the calculator refuses to re-scale its own product →
'same size' at EVERY setting → the app that did it
RIGHT gets the worst score on the page"]
  style UNSUP fill:#ffd7d4,stroke:#d9463b,stroke-width:2px
  style R1 fill:#fff,stroke:#d9463b,stroke-dasharray:4 4
  style R2 fill:#fff,stroke:#d9463b,stroke-dasharray:4 4
  style R3 fill:#fff,stroke:#d9463b,stroke-dasharray:4 4
The root defect, in one line: the loop measured what the calculator can compute, which is a property of iOS's scaling curve and nearly identical for every font — instead of what this label would render, which depends on two things the loop never read: the app's opt-in flag, and whether iOS itself created the font.

3 · What we changed — judge the element, not the font curve

Instead of asking a calculator a question whose answer is the same for every font, the engine now asks, per element: "would this view actually render bigger text at larger settings?" — using the same conditions iOS itself applies.

flowchart TD
  A["Text element"] --> B{"What kind of font?"}
  B -- "real text style
(Apple's Dynamic Type fonts)" --> C{"Did the app opt the view in?"}
  B -- "custom size built the
recommended way (UIFontMetrics)" --> C
  B -- "plain fixed font
(iOS will never scale it)" --> F["does NOT scale"]
  C -- yes --> D["scales — check every setting
from XL up to the 200% point"]
  C -- no --> F
  D --> E{"any setting where
it would not grow?"}
  E -- no --> P["Text Magnification: PASS"]
  E -- yes --> V["fails exactly those settings —
they are listed in the finding"]
  F --> V2{"can we be sure? see §5"}
  V2 -- yes --> FAIL["VIOLATION"]
  V2 -- no --> NR["NEEDS REVIEW"]
  style P fill:#d7f0dd
  style FAIL fill:#ffd7d4
  style NR fill:#fff3cd
①fixed by the band — the default setting is the curve's fixed point, so it is excluded; the check runs only where text is supposed to grow: XL up to the 200% point ②fixed by the two new questions — did the app opt the view in, and did iOS vend the font? A plain fixed font now correctly fails every band setting ③fixed by re-reading the refusal — "refuses to re-scale" is exactly the fingerprint of a font that was built the right way; it now classifies the font as scalable instead of condemning it

Old flow: a healthy label, a broken label and a best-practice label were indistinguishable (byte-identical or inverted evidence). New flow: three different, correct answers — and the violation now names the exact settings that fail.

Text Truncation now builds on the same answer: only text that will actually grow can newly get cut off. For growing text it measures the enlarged string against the element's real space — and treats wrapping, scrolling and shrink-to-fit as what they are: ways of accommodating growth, not losing content. Text that never grows can't truncate at 200% (it has the other problem, which Text Magnification reports — one root cause, one finding, not two).

5 · The new verdict: Needs Review — and when you'll see it

Some apps scale text through their own code, in ways no automated check can observe without physically changing the device's text-size setting. Asserting a violation there would be guessing. Three patterns route to Needs Review instead:

PatternExample from the eval appsWhy automation can't be sure
App-custom text machinery — the element or its wrapper is the app's own class Spotify wraps every label in its own OBJC_ONLY_Label — and really does scale text through its own pipeline (verified on device at 200%) Custom code can react to the real settings change while ignoring a per-element probe
System chrome — text inside navigation / search bars Navigation titles, search-bar placeholders iOS owns their rendering and provides its own large-type affordances (like the tab-bar long-press viewer)
Editable-input text — a field or its placeholder Discord / B&BW / noplace input fields Placeholder rendering is field-managed; Text Truncation already excludes inputs for the same reason
Violation — measured: this element will not scale, and the app owns the fix Needs Review — verify manually at 200% text size Pass — measured: scales across the whole band Not considered — system-owned labels (tab bars, buttons, segments)

6 · Same data, opposite truths — why Needs Review is honest

Spotify — "Continue with Apple"

Fixed custom font, no opt-in flag. Really does scale at 200% (own machinery). Old rule: violation.

Now: NEEDS REVIEW — custom machinery detected, verify manually

Smule — "Fixed 17pt" style labels

Fixed font, no opt-in, plain UIKit label — really does not scale. Old rule: violation (for the wrong reason).

Now: VIOLATION — measured per element, for the right reason

The two used to be indistinguishable in the data — the fix is that indistinguishable cases are now labeled as such rather than guessed.

7 · Findings got more informative, too

The "unsupported font sizes" list in each finding is now a per-setting measurement across the whole range between default and 200% — not a constant:

ElementOld finding saidNew finding says
Fully non-scaling labelone meaningless entry (the same for every font)all five failing settings, XL → 200%
4pt fine-print label (rounding quirk)same meaningless entryexactly the one setting it really fails (XL)
Properly scaling labelsame meaningless entry → false violationempty — passes

8 · Proof: a purpose-built test app

A fixture app with 21 labeled cases (every scaling pattern: text styles, UIFontMetrics fonts, fixed fonts, opt-in-without-scalable-font, capped fonts, shrink-to-fit, self-sizing, custom scalers, system controls, inputs) now runs as the regression bench. Current score:

MetricBefore this workAfter

9 · What's deliberately left open

The endgame is measurement, not prediction: scanning the same screen at default and at 200% and comparing what actually rendered would resolve every Needs Review automatically — including app-custom scalers — and is the one approach that can't be fooled. Design and trade-offs: the companion page. Also tracked: system-control detection by ancestry rather than class names (new iOS versions rename internal classes), and fonts capped by the app below the 200% size, which today read as scaling.
