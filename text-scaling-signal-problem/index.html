One signal, two truths — why static font inspection cannot judge text scaling

iOS App-A11y · font-magnification-support (Text Magnification) & text-truncation · WCAG 1.4.4 · running examples from the TM/TT eval corpus (26 scans, 8 apps, vendor + dev adjudicated)

1 · How the signal is manufactured

Capture inspects the element's UIFont at default text size and predicts scaling support per content-size category:

The tautology: UICTContentSizeCategoryL (.large) is the reference point of the UIFontMetrics curve — scaling at .large is scaling by 1.0×, so scaledFont.pointSize == font.pointSize holds there for every font in existence. Result: 408 of 408 font-bearing elements in the corpus carry ["…CategoryL"], and for every one of the 38 vendor/dev-marked rows it is the entire evidence. The field is a constant, not a measurement.

2 · The problem: true and false positives are byte-identical

Two elements, captured on the same pipeline. Their rows are indistinguishable — their real behavior at 200% is opposite.

Spotify — "Continue with Apple"

font=SpotifyMixUI-Bold 16.0pt
supportsDynamicFont=0
unsupportedFontSizes=[L]

At 200% the app scales the text through its own mechanism (and adaptively shortens the label to "Apple" — WCAG-compliant re-presentation, a11y label keeps the full string).

Rule says: VIOLATION → false positive

Smule — "Rock" (genre label)

font=.SFUI-Semibold 15.0pt
supportsDynamicFont=0
unsupportedFontSizes=[L]

At 200% nothing changes — fixed-size systemFont(ofSize:), no text style, no adjustsFontForContentSizeCategory, no custom scaler.

Rule says: VIOLATION → true positive
The separating fact — does the rendered text grow at 200%? — never enters the capture, because the scan renders the screen at default size only. Growth driven by app-custom scaling (Spotify) is invisible to any inspection of fonts, flags or properties. Every static predicate therefore classifies these two elements identically.

3 · What breaks if we "solve" the FP with static signals

Each candidate fix clears the Spotify row — and takes confirmed true positives (or a silent miss-class) with it:

Candidate static fixClears the FP?Collateral damage — concrete corpus examples
Filter the [L] artifact out of the rule's inputyes All 17 dev-confirmed TM true positives go silent — Smule genre labels ("Rock", "Pop", …), PayPal "Pay Later" buttons (18pt), B&BW search field (14pt), YouTube Music sign-in labels — their evidence is the identical [L].
Gate on supportsDynamicFont == 1 (mark N/A otherwise)yes Same wipeout: Smule/PayPal/B&BW TPs also carry supportsDynamicFont=0. Plus every legacy/WDA-path tree defaults the absent flag to "0" (flagString has no tri-state), so the rule dies wholesale off-device.
Gate on adjustsFontForContentSizeCategoryno Spotify scales without that flag (custom mechanism) — still misread. And labels using preferredFont(forTextStyle:) without the flag scale on next screen creation / relaunch — real violations of the opposite kind become invisible.
Capture more static properties (text style, metrics wrapper, …)no Still a prediction from a single default-size render; app-custom scalers and runtime re-labeling remain out of reach. New fields inherit the same absent→"0" landmine on every non-fresh path.
General statement: any predicate computed from a single default-size capture that clears the Spotify false positive also clears the Smule true positive. This is not a tuning problem — the information needed to separate them is absent from the input.

4 · The only solution that actually works: measure, don't predict

Capture the same screen twice — default and accessibilityLarge (200%) — match elements, and compare what actually rendered. The device cloud already controls the device settings; the capture pipeline already extracts per-element rendered data; element-matching machinery (identity attrs / fingerprints) already exists.

Cost, honestly: one extra render + capture per scan, an element-matching step across the two renders, and one residual judgement call (when text changes at 200%, is the shorter form an equivalent? — assistable via a11y-label containment). Everything else on the table is a cheaper way to be wrong: it predicts a behavior the capture never observed, from a field that is constant by construction.

Interim state until dual-capture ships: PR #277 (system-label exclusion) and PR #278 (removes the .large artifact from text-truncation's clip heuristic, on-device only) eliminate the systematic TT false-positive engine while deliberately leaving text-magnification's input untouched — precisely because of section 3.
