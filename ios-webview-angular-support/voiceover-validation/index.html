Does what we capture match what VoiceOver says?

iPad Air 11" (M2), iPadOS 26.5 · Angular Rule Lab · VoiceOver output captured for every element of all 41 rule pages with the iOS accessibility audit service (pymobiledevice3 developer accessibility list-items, the same engine Accessibility Inspector uses for its VoiceOver "spoken description"; VoiceOver itself cannot be toggled remotely) · our capture = the read-only in-process DOM layer (v5) scans · plus a 44-min screen recording of real VoiceOver navigating every rule page (watch the recording). Its on-screen caption panel was OCR'd at 2 fps; the full announcement after each pause is kept. · 1 Oct 2026

Key findings

  • Names are right. Against real VoiceOver (screen recording), the accessible name we capture agrees for 94% of 249 matched elements. Identical wording, ignoring hints such as "Double-tap to…" and landmarks such as "end, main", is 75% for our capture and 69% for the audit service.
  • The audit service is not a perfect proxy for VoiceOver's speech. Its roles differ from what VoiceOver says: it drops "Text field" and "Tab", and turns checkboxes and switches into "0/1, Button, Toggle". Real VoiceOver says "Checkbox, ticked", "Switch button, on" and "Radio button, ticked, 1 of 2". Our capture is closer to real speech than the audit service is.
  • What our caption still lacks: the state word for checkboxes, switches and toggle buttons (VoiceOver says ticked / unticked, on / off, Pressed after the role; for tabs it prefixes "selected", as we do), a field's value and "Multi-line text field", the heading level ("Heading level 2"), the list position ("1 of 2"), and a disabled word for disabled controls (audit: "Not Enabled"; not exercised in the recording). "Tab" should not carry an extra "Button".
  • Images: VoiceOver drops a redundant "image" word from the name ("Profile image" → "Profile, Image"), and an SVG used as an <img> is read by its inner text ("50% OFF") rather than its alt.
  • Order and reachability (§4). The order we capture inside the WebView is VoiceOver's order: the same on all 5 reading-order test cases, and 99.9% of element pairs agree with the audit-service swipe order across all pages. The recording confirms 18 of the 22 expected-FAIL test cases in §4. Of the rest, 2 do not reproduce for VoiceOver (MRO TC3's DOM is not interleaved; traversal TC1 traps keyboard focus only) and 2 VoiceOver cannot judge. 3 test cases are excluded after manual review. Our capture holds the right signal in 33 of 33 judgeable rows.
  • AI inputs (§5). Headings (is_heading 10/10), image candidates (5/5, bbox exact), link and input labels are correct. MRO never runs on a dylib capture: the server takes the iOS focus order only from a VoiceOver caption, and the dylib has none. Screen Reader Focus is gated the same way. Our DOM order could fill that focus order; the visual-order sequence (sorted by y, then x) must not.
  • Verdicts: the label rules have 0 false positives on the test cases. Recall is limited by AI-pending checks and iOS rule semantics, not by wrong names.

6 · Property mapping: HTML → the iOS keys the rules read

The iOS rules were written for UIKit and read UIKit-shaped keys (type, label, traitsStringArray, isWDAccessible, textProperties…). For a WebView element there is no UIKit view. The DOM layer reads the HTML (tag, ARIA attributes, computed style, layout) and fills the same keys, so the rules run unchanged. Source: bsWebDOMExtractorJS and bsMapWebNodes in AppAccessibility.swift (branch webview-dom-poc, v5 c9ad546).

Is that the right source under WCAG? Yes, in principle. For web content, WCAG defines name, role, state and value (4.1.2), structure (1.3.1) and the rest on the content itself, as exposed to assistive technology through the browser's accessibility API. The mapping from HTML to that API is standardised: HTML-AAM, Core-AAM and AccName 1.2. WebKit implements it to build the objects VoiceOver reads. So deriving the keys from HTML measures what WCAG measures. UIKit properties of the WKWebView itself would not. The risk is not the source but three implementation gaps:

  1. Where our JavaScript re-implementation of those specs diverges from WebKit's own computation.
  2. Thresholds tuned for UIKit points applied to CSS pixels.
  3. Properties computed in the extractor and then dropped before the rules see them.

The ground truth is available: Web Inspector's DOM.getAccessibilityPropertiesForNode returns WebKit's own computed values, and matched the extractor on 10 of 10 names in the earlier probe.

Computed by the extractor but dropped before the rules

bsWebDOMExtractorJS already returns these, but bsMapWebNodes does not copy them into the node, so neither the rules nor the AI requests see them:

  • ac = autocomplete, ht = input type, it = inputmode: exactly what 1.3.5 Identify Input Purpose (input-type-for-input-field) needs. Today the AI judges from the label and pixels only (§5).
  • lvl = heading level (aria-level or h1–h6): VoiceOver says "Heading level 2"; incorrect-heading hierarchy checks and the caption could use it.
  • dyn = system-font flag: unused since v5 (text magnification is N/A for web).

Set as constants rather than computed: isPotentiallyObscured="0", isWDFocused="0", hasKeyboardFocus="0" (document.activeElement is never read), alpha=1, isWDAccessibilityContainer="0", showsLargeContentViewer="0". The first three matter: the images-of-text AI request has an isPotentiallyObscured field (always empty today, §5), and the focus rules would use the focused element.
