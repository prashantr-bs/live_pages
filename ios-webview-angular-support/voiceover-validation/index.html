Does what we capture match what VoiceOver says?

iPad Air 11" (M2), iPadOS 26.5 · Angular Rule Lab · VoiceOver output captured for every element of all 41 rule pages with the iOS accessibility audit service (pymobiledevice3 developer accessibility list-items, the same engine Accessibility Inspector uses for its VoiceOver "spoken description"; VoiceOver itself cannot be toggled remotely) · our capture = the read-only in-process DOM layer (v5) scans · 1 Oct 2026

322captured accessible web elements compared with VoiceOver
72%spoken output identical (232)
94%accessible name identical (303); the rest differ only in role/state wording or name
100% · 61%label-rule precision · recall vs expected verdicts (TP 28, FP 0, FN 18, TN 14; 19 AI-pending excluded)

Key findings

  • Names agree. For the label rules, the accessible name we capture matches VoiceOver for 94% of elements. Exact spoken-output agreement is 72%; the remainder is mostly role and state wording.
  • Text fields: VoiceOver's caption is name, value-or-placeholder with no role word ("PIN code, Enter PIN code"). We append "Text field".
  • Checkboxes and switches are announced "…, 0 / 1, Button, Toggle". Our caption says "Checkbox" or "Switch button". Rules that read spoken output should use VoiceOver's vocabulary.
  • Headings come out as "…, <level>, Header", and disabled controls as "…, Button, Not Enabled". We emit "Heading" and no disabled word.
  • A selected role=tab is announced with no role at all ("Home selected, Selected"). By VoiceOver's own output that is a real missing-view-type defect, but we mark it "Button, Tab" and pass it.
  • An SVG used as an <img> is announced by its internal text ("50% OFF"), not its alt. Inline links split the surrounding text into separate items.
  • Verdicts: label rules have 0 false positives on the test cases. Recall is limited by AI-pending checks and the iOS rule semantics noted on the POC pages, not by wrong names.
