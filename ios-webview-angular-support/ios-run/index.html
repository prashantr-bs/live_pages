iOS run: AppA11y Rule Lab (Angular + Ionic in WKWebView)

On-device scan of every rule page · iPad Air 11" (M2), iPadOS 26.5 · BrowserStackInjector v119 (codesigner master @ bb6b75d4, 30 Sep 2026) · on-device rule engine 2.4.0 · app: Angular 22.2 + Ionic 9.0.5 + Capacitor 8.5.2 (~/Work/AngularFrameworkPOC on the Mac mini) · Android talkback run: to follow

47scans (every scroll position of 41 rule pages)
208test cases, all fully on screen in ≥1 scan (127 expect FAIL)
1,263nodes captured, all WebKit layer / UIKit plumbing
0nodes carrying web-derived label / text / value
0FAIL results emitted (vs 127 expected)
Root cause, common to every rule: Web content never becomes nodes: the walk (processViewIteratively over UIView.subviews + accessibilityChildrenOf) only sees WebKit's layer views; WKWebView text/colour/font is nil (extractTextColorFontAndMetrics, :3400); no JS / DOM access anywhere. Result: of 41 rules, 34 emit nothing at all; overlapping-interactive-elements and responsive-containers emit only vacuous / misleading PASS rows on UIWindow / WK* containers; app-orientation-support is the one rule that genuinely works (app-level plist check); 4 rules are Android-only and do not exist in the iOS engine.

Method

  1. Built the unsigned device IPA and injected codesigner/bin/BrowserStackInjector (v119) as @executable_path/Frameworks/BrowserStackInjector. reveal-inject/reveal-install.sh --skip-reveal wrapped it as BSI.framework, signed it with plumesign (free Apple ID, com.commonbundle.someapp) and installed it.
  2. Enabled Web Inspector on the iPad; the app sets webContentsDebuggingEnabled. pymobiledevice3 webinspector cdp exposed the WKWebView as a CDP target.
  3. scripts/ios-scan-all.mjs (POC repo): for each rule, navigate the WebView to /rule/<id>, step ion-content by 85% of the viewport, record which test cases are fully visible, then run reveal-inject/a11y-scan.sh (GET :1234/accessibility_info?on_device=true&framework=native) → snapshot.json + screenshot.png.
  4. scripts/score-ios-scans.py joins the rule results with docs/TEST_CASES.md (expected verdicts) and walks every snapshot tree for web-derived content.

Gotcha observed: the dylib dedupes on tree-MD5 or screenshot-MD5 across the whole app process (AppAccessibility.swift:1188), so re-scanning an already-seen page returns status: duplicate until the app is relaunched. Two such re-scans were redone after a relaunch.
