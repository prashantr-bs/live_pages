0 · TL;DR

Today: web content is invisible

The dylib walks UIView.subviews and UIAccessibility containers in the app's own process. A WKWebView's content lives in WebKit's separate WebContent process. Under WKContentView the walker only ever gets one unlabeled AXRemoteElement proxy covering the whole web area.

0 of 37 rules evaluate in-page web elements

The failure mode is silent

Nothing marks a web region as "not assessed", so a fully hybrid screen reads as clean. Capacitor-framework snapshots (typically Ionic/Angular) average 0.02 failing rows each, against 5.09 for native. A 100%-WebView Cordova screen got pass on every rule except app-orientation.

false negatives that look like compliance

Can it be fixed? Yes, via the DOM

Reliable path: from the dylib, inject a script into each WKWebView in an isolated WKContentWorld (iOS 14+, bypasses page CSP). It reads DOM semantics, rects and computed styles (axe-core or ports of our rules) and maps rects to screen points. Contrast stays pixel-verified on the screenshot.

23 rules High, 10 Medium, 3 N/A (§5)
Hard limits, whatever we build: SFSafariViewController and ASWebAuthenticationSession are out-of-process and opaque to the host app. Closed shadow roots, <canvas>/WebGL UIs (e.g. Flutter-web CanvasKit) and truly cross-process iframes (WebKit site isolation) cannot be read from the page. They should be reported as "web content not assessed", never as pass.
Angular in one line: NativeScript-Angular renders real UIKit and is supported today like native. Every other Angular-on-iOS shape (Ionic + Capacitor, Ionic/Cordova, an Angular site inside an app's WKWebView) is WebView content and is currently blind. Angular adds little difficulty on top of "any SPA in a WKWebView": open shadow roots (Ionic/Stencil, ViewEncapsulation.ShadowDom), SPA route changes as scan triggers, and a usable "DOM is stable" signal (getAllAngularTestabilities().whenStable when present). §9.

iOS (this page) code

  • Capture is synchronous on the main thread. The TCP listener runs on .main (TcpServer.swift:375).
  • Children come from subviews, plus accessibilityElements / accessibilityElementCount() for non-UIView proxies (accessibilityChildrenOf, AppAccessibility.swift:1782). This was built for Flutter SemanticsObjects.
  • Framework is passed in (framework=), not detected. The engine enum is native | flutter | react_native | cordova, and cordova is never read by any rule (BSRuleEngine.swift:27).

Android (contrast only) code

  • talkback's AccessibilityService reads the system AccessibilityNodeInfo tree. Chromium's AX bridge exposes WebView DOM nodes as virtual nodes ("the only representation of real content", BSRuleHelpers.kt).
  • So Android already sees web elements and has web carve-outs (focus order, ad WebViews). iOS has no equivalent input.

2 · What the scanner captures at a WebView

2a · Code code

The only WebView special case in capture is a short-circuit that gives up on text, colour and font (AppAccessibility.swift:3400, extractTextColorFontAndMetrics):

if view is WKWebView {
  NSLog("[AppAccessibility] Detected WKWebView - text extraction requires JavaScript evaluation")
  // For WKWebView, text/color extraction would require async JS evaluation
  // which is not suitable for synchronous property extraction
  return (nil, nil, nil, nil, nil, nil)
}
  • There is no evaluateJavaScript, WKUserScript or WKScriptMessageHandler anywhere in the dylib. Nothing reads the DOM, and nothing forces the web AX tree to build.
  • WKContentView, WKCompositingView, WKChildScrollView, UIWebView, SFSafariViewController and _UIRemoteView have no special-casing. They are walked as generic UIViews and are not in the capture-time OCR class allow-list (:2737). Full-screen OCR only enriches existing text nodes; it never creates nodes.
  • WKWebViewInspectableMocker (forces isInspectable, iOS 16.4+) is gated on the webviewInspect patch flag, which realmobile sets only for App LCA sessions (LCAM-2671, §7b). Nothing in App A11y reads it.

  • WKContentView does not implement accessibilityElementCount/accessibilityElementAtIndex. It only registers ax-uuid/ax-pid tokens so that the accessibility bundle can bind to the WebContent process. WKContentView.mm
  • The per-node API (label, traits, frame, ARIA) is implemented by WebAccessibilityObjectWrapperIOS inside the WebContent process. WebAccessibilityObjectWrapperIOS.mm · WebPageIOS.mm
  • AXRemoteElement (private AXRuntime) holds remotePid/machPort/uuid. It is a proxy only. AXRemoteElement.h. Texture hit exactly this: "WKWebView's accessibility elements are handled out-of-process". Texture#1955
  • The web AX tree is lazy. Document::axObjectCache() returns null until an AX client enables accessibility, and the WebContent sandbox only unblocks AX mach services after kAXSApplicationAccessibilityEnabledNotification. Document.cpp · WebProcessProxyCocoa.mm
  • This is why XCTest/WDA can list web elements: it is the out-of-process client. It is also why WDA page source with web content is slow and sometimes truncated. appium#9408 · WDA slowness

Reusable for App A11y inference

  • Unlock is free: App A11y sessions already inject BrowserStackInjector, and the shipped binary already contains the mocker. The only change is letting realmobile append webviewInspect for App A11y sessions, as a gate change; no dylib rebuild.
  • JS channel exists: once pages are inspectable they appear on the device's webkit proxy. realmobile can Runtime.evaluate an extractor or axe-core per page, without Appium.
  • A quick way to prototype the §8 extractor: the same JS can run host-side first, then move in-process unchanged.

Why it is not the end state

  • Mapping: the host sees pages, not views. It must match each /json page to a WKWebView frame (order is not screen order) and combine it with getBoundingClientRect. In-process, the frame is known directly.
  • Contention: the per-device proxy is shared with Appium (App Automate) and App Live DevTools.
  • Timing: the host round-trip is separate from the dylib's capture of screenshot + tree, so the DOM can drift between the two.
  • Same hard limits: SFSafariViewController / ASWebAuthenticationSession, closed shadow roots, canvas, per-frame injection for cross-origin iframes.
Net: LCAM-2671 does not add accessibility scanning. It does remove the two costliest prerequisites for a host-side PoC: inspectability on iOS 16.4+ and a live WebKit inspector channel on every device. Recommended sequencing: (1) ship the "web content not assessed" marker; (2) PoC the DOM extractor host-side through webviewInspect + ios_webkit_debug_proxy on the Angular POC app; (3) move the same extractor in-process (§8) for production.

Why it is reliable research

  • Public API: callAsyncJavaScript(_:arguments:in:in:) awaits Promises, and its completion runs on main (iOS 14+). Apple
  • Isolation: WKContentWorld gives our globals a separate world over a shared DOM, so page scripts cannot tamper with them. Apple
  • CSP-proof: WebKit enables eval in any non-normal world regardless of page CSP (ContentSecurityPolicy.cpp).
  • Finding webviews: the walker already meets every WKWebView, and the dylib already swizzles WKWebView init (inspectable mocker), so a weak registry is cheap.
  • Async precedent: Flutter semantics enablement already spins the run loop with a bounded poll before capture (AppAccessibility.swift:442-532).

Engineering points to get right

  • Threading: never block main waiting on JS; the completion is delivered on main and would deadlock. Kick off JS first, then run the native walk, then merge with a timeout.
  • Coordinates inference, validate: getBoundingClientRect + scrollX/Y gives document CSS px, which equals the WKContentView coordinate space. Then contentView.convert(_:to: nil) handles zoomScale, contentOffset and insets. ×scaleFactor for screenshot px.
  • Frames: WKUserScript(forMainFrameOnly:false) covers frames created after install. Existing cross-origin or site-isolated iframes may be unreachable, so report them as not assessed.
  • Shadow DOM: recurse into element.shadowRoot (open). Closed roots are unreachable, so flag the host.
  • Accessible name: use a proven implementation (axe-core's, MPL-2.0, ~0.5 MB minified) or dom-accessibility-api; don't hand-roll accname.
  • Visibility: exclude display:none, visibility:hidden and aria-hidden subtrees for visual rules, but keep cdk-visually-hidden / sr-only text for name rules.
  • Noise gate: skip 0×0 or 1×0 webviews (analytics/payment SDKs, §3) and webviews that are <x% visible or covered.
  • Budget: cap nodes (e.g. 1,500) and time (e.g. 3 s); record webCapture{ms,nodes,truncated,reason} in performance.
Two build shapes: (1) Run axe-core in-page: fastest to breadth (90+ rules, battle-tested), but its results must be mapped into our 37 rule ids and severities, and its contrast is CSS-only. (2) Web branch per BS rule: a small in-page extractor emits a normalised node list (role, name, states, rect, styles). The existing Swift rules each get a web branch, which keeps rule ids, messages and AI candidate plumbing identical and adds the screenshot-verified contrast. Recommendation: ship (2) for parity, and borrow axe's accname/role computation as a library.
Not coverable from the dylib, so report "not assessed" with a reason: SFSafariViewController / ASWebAuthenticationSession (out of process; seen 9× in 7 days), closed shadow roots, canvas/WebGL UIs (Flutter-web CanvasKit, game engines, map tiles), site-isolated cross-origin iframes (payment widgets), PDF rendered inside WKWebView, and UIWebView (deprecated, 58 snapshots/7 d, in-process legacy — may be partially reachable but not worth building for).
