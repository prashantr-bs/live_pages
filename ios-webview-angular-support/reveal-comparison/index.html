Reveal vs App Accessibility on WebView content

The 6 rules App Accessibility doesn't support on WebView content, checked against Reveal 58 (RevealServer injected into the same Angular + Ionic Rule Lab on the iPad Air, iPadOS 26.5). For each rule: the closest Reveal Insights rule, what our DOM-layer POC captures, and what Reveal captured on the same screen. Hover or focus a box for details.

Summary
  • Reveal is blind to WebView content. In all 5 snapshots, Reveal's accessibility tree for the screen is a single AXRemoteElement covering the whole web view, with no label, no traits and no children. Its view tree contains only WebKit drawing layers (WKCompositingView). The only labels anywhere in its capture are the scroll bars. The page's elements live in WebKit's own process, and Reveal, like the stock dylib, only reads in-process objects. So none of Reveal's 138 Insights rules can evaluate a web element.
  • For these 6 rules, Reveal adds nothing on WebViews. Its closest rules (traversal order, focusable control, focus trap, font scaling, label wording, redundant state) are UIKit / accessibility-tree checks with nothing to read. Three of them (focus trap, font scaling, redundant state) are also narrower than ours on native screens.
  • On native screens Reveal's coverage of our rule set is lower, not higher. Of our 37 iOS rules, 26 have a same or close Reveal rule, 6 only a partial one, and 5 none (images of text, visual order, non-text contrast, keyboard focus, two-dimensional scroll). Our AI-judged checks (heading meaning, alt-text quality, link context, input purpose) are only empty-label or regex heuristics in Reveal. Reveal does add checks we lack: hint wording, HIG typography, dark mode and Increase Contrast, gesture alternatives, focus-indicator visibility, and colour-blind / APCA contrast.
  • App Accessibility already has the data for two of the six. The DOM layer captures the reading order (matches VoiceOver) and hidden-but-tappable controls. Meaningful Reading Order needs a server-side caption fix, and Screen Reader Focus needs the caption on device.

Meaningful Reading Order

meaningful-reading-orderNeither today; App A11y is one server fix away.
App Accessibility (POC)Not run. We capture the DOM order, which matches real VoiceOver on 5 of 5 test cases, but the server can’t match the VoiceOver caption to web nodes, so the AI is never called.
Reveal: WCAG22A-004 · Potentially Confusing Traversal OrderCompares each element’s VoiceOver traversal order with its position on screen. On WebView: Has no web elements to order.

Screen Reader Focus for Interactive Elements

focus-order-for-interactive-elementsNeither; App A11y has the data.
App Accessibility (POC)Rule never runs on device (it waits for a VoiceOver caption, PAAA-606). The capture already has the signal: TC1–TC3 are hittable but hidden from assistive tech (red).
Reveal: WCAG22A-007 · Focusable ControlFlags an interactive view that isn’t exposed to accessibility. On WebView: Sees no web views, so it can’t flag hidden web controls.

Traversal Order Cycle

traversal-order-cycleNeither.
App Accessibility (POC)Not applicable on iOS: no traversal-cycle data, native or web.
Reveal: WCAG22A-008 · Potential Focus TrapOnly flags a right-to-left / left-to-right direction mismatch between neighbouring elements. On WebView: Doesn’t detect real cycles, and sees no web elements.

Font Magnification Support

text-magnificationNeither on WebViews.
App Accessibility (POC)N/A for web content: checking it would mean changing the page.
Reveal: WCAG22AA-007 / HIG-015 · Font Does Not ScaleChecks UIKit text views for adjustsFontForContentSizeCategory. On WebView: Web text isn’t a UIKit label, so the property doesn’t exist.

Spoken Description not Meaningful

screen-reader-for-interactive-elementsNeither on WebViews.
App Accessibility (POC)The iOS rule only checks the element is accessible. The names are captured correctly (“btn_submit_01”, “ic_settings_24dp”, “ ”).
Reveal: WCAG22AAA-001 Non-Specific Label · WCAG22A-019 Empty Control Label · HIG-029 File Name in LabelRegex and empty-label checks on accessibility labels. On WebView: Its label checks would catch TC3 (whitespace) on a native screen; it sees no web labels.

Duplicate State Info in Spoken Output

state-in-content-labelNeither.
App Accessibility (POC)The iOS rule only flags a doubled “selected”; “checked”, “on” and “enabled” in labels are missed. Names are captured correctly.
Reveal: ABP-002 · Redundant Element Type In Label (“selected” clause)Flags a label containing “selected” on a selected element. On WebView: Same narrow vocabulary, and sees no web labels.
