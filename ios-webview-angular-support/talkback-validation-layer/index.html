Key findings

  • The capture is a faithful copy of TalkBack's speech. For 93% of 290 distinct element announcements our captured spokenDescription is word-for-word what TalkBack said (after removing TalkBack's list / pager context such as "In list, 41 items" and "1 of 2", which is not part of an element). Almost all of the remaining rows are OCR slips in the recording ("Cancei", "71,299", "lmage").
  • One real wording gap: switch state. For role=switch and ion-toggle, TalkBack says "On, Dark mode enabled, Switch" / "Off, Dark mode switch, Switch". Our capture says "ticked, Dark mode enabled, Switch", sometimes "ticked, on, …", and drops "Off". (For an aria-pressed toggle button TalkBack itself says "ticked, Wi-Fi, Switch", and our capture matches.)
  • The defects are audible. Of 127 expected-FAIL test cases, real TalkBack shows the defect in 68; 43 are visual or keyboard rules that speech can't reveal, and 5 don't reproduce (e.g. CSS-uppercased "CANCEL", the row-major reading order of MRO TC3).
  • POC + DOM layer: 72 of 127 expected-FAIL test cases reported FAIL (stock replay: 6), 35 sent to AI / needs review, 37 missed, 0 false alarms on expected-PASS test cases. Of the 68 defects TalkBack users actually hear, it reports 39 as FAIL, sends 10 to review and misses 19 (list below, with the reason each is still missed).
  • What the DOM layer adds: label relations, computed CSS (colours, sizes, spacing, text-transform), event listeners and DOM / tab order from a host-side CDP capture, merged onto the Android web nodes. That is where the extra TPs over the Chromium-only POC come from; the misses that remain are mostly AI rules, Android-native parity and cases that do not reproduce on this screen.
  • How TalkBack treats labels in a WebView (checked on the phone): a <label>-associated field or checkbox is read as the label text and then a bare "Edit box" / "Tick box". Chromium gives the control no name, and our capture does the same. Rules that check "has a name" will flag these controls, so they need to use the label relation, or the preceding label item, to avoid false positives.
  • Screen Reader Focus reproduces exactly as on iOS: the aria-hidden button (TC1), the card inside an aria-hidden container (TC2) and the role=presentation image (TC3) are never reached by swipe.

Why is the class android.widget.*? Is it translated to a native view first? What is more accurate?

Yes, Chromium translates it. A WebView has no Android views inside it. Chromium publishes the page's accessibility tree to Android as virtual AccessibilityNodeInfo nodes and has to give each one a class name. It maps the web role onto the closest Android widget class. The capture records that node as it is, which is why the report shows it. Data from all 69 scans (Android class against the matching DOM element):

44: how do we get the font size? Is it px only, from Chromium?

Chromium gives no font size for web text. Every web TextView in the snapshot has fontSize, textSizeInPx and fontSizeUnit null (Chromium's virtual nodes return no ExtraRenderingInfo), and its per-character boxes are just the node rect repeated.

  • Chromium-only POC (BSWebContent.kt:23 lineBoxPx): uses the line-box height in physical px ÷ density (2.75) as the size.
    • The line box is about 1.3× the font size, so this can only miss, never over-report.
    • The 9 / 11 / 13.5 / 14 / 16 px test cases came out as 12.0 / 13.8 / 17.1 / 18.2 / 20.0, so TC3 (13.5 px) was missed.
  • DOM layer (BSWebLayer.kt:131-134): reads the computed CSS font-size, which is in CSS px.
    • The rule compares CSS px directly with the 14 threshold (shown as desired_font_size 14.0, font_size_source web_css).
    • In a WebView, 1 CSS px = 1 dp (device pixel ratio = display density), so 14 CSS px is the same physical size as a native 14 sp/dp text at font scale 1.0.
    • TC1–TC3 now FAIL with 9.0 / 11.0 / 13.5.
  • Two limitations:
    • System font scale is not captured. The scan has neither fontScale nor the WebView's textZoom. A WebView scales text with the system font size, and it is unverified whether getComputedStyle then reports the scaled size. The fix is to capture textZoom/fontScale and divide by it, for parity with sp.
    • Some chips fall back to the line box. The "Expect FAIL" chips are 13.8 (web_line_box) because the DOM box and the Chromium box differ by 17 px (padding), beyond the 8 px matching tolerance.

The many other readable-text-size findings are the Rule Lab's own 11–13 px labels, which are real by this rule.

45: why are TC2 and TC3 not violated for Readable Text Spacing?

The rule checks only two things (web arm BSAdditionalRules.kt:2947-2964, same as the native Ruby rule):

  • Line height ≥ 1.5 × font size, only for text with 2+ lines.
  • Word gap (0.25 × font size + word-spacing + letter-spacing) ≥ 0.16 × font size.

There is no paragraph-spacing or letter-spacing check. The native rule defines PARAGRAPH_SPACING_MULTIPLIER and calculate_paragraph_spacing but never calls them.

  • TC2 (two paragraphs with no gap): each is one line, so line height does not apply, and the word gap is 4.0 ≥ 2.56. PASS.
  • TC3 (letter-spacing:-0.8px): one line, word gap 3.2 ≥ 2.56. PASS.
  • TC1 (line-height = font size over 2 lines) FAILs correctly.

Verdict: TC2 and TC3 test checks the rule does not have. Add a web paragraph check (gap between sibling text blocks ≥ 2 × font size) and a letter-spacing floor, or mark these TCs out of scope.

Noise on this page: any wrapped text with line-height: normal is assumed to be 1.2 × and fails (the page intro, the TC4 description).

What is the limitation for the focus order of WebView elements? Do we get it right?

The capture records no web focus order. In every scan, the snapshot's focusOrder is a single entry, "Web view", and keyboardOrder holds only the WebView. Every web node has traversalIndex and focusOrder −1. When TalkBack's swipe reaches the WebView, it hands navigation to Chromium (next HTML element), so TalkBack's own traversal never lists the web elements.

What the engine does instead. For Meaningful Reading Order (BSAIRules.kt:545-598), the POC builds the order itself: Chromium's virtual nodes in tree order (Blink's accessibility-tree order, i.e. DOM order after aria-owns and shadow-DOM slotting), keeping the nodes TalkBack would stop on.

  • On scan 33 that gives "3·Pay → 1·Cart → 2·Address", "Total → ₹2,450", "Name → Email → City → Zip", "Buy → Wireless earbuds → ₹3,999".
  • That is exactly what real TalkBack did on TC1–TC4 in the recording. CSS order, flex-direction:*-reverse, grid placement and absolute positioning are correctly not applied, which matches TalkBack.

Limitations:

  • The order is synthesized, not recorded. Our rule for which nodes TalkBack stops on only approximates Chromium's own navigation, which merges and skips some nodes.
  • Only on-screen nodes: TalkBack keeps going while scrolling; a scan is one viewport.
  • The order exists only in the AI candidate, not in the snapshot, so nothing else (and no report view) can use it.
  • Keyboard (Tab) order is not available at all. The DOM layer carries tabindex only. The offline probe cdp_layer/tabgraph.mjs does find the Tab traps (TC1 Card→Expiry→CVV→Card, TC2 Option A↔B, TC3 the modal), but it is not wired into the engine.

  • Traversal Order Cycle reads Android traversalBefore/After, which Chromium never sets, so it finds nothing in every variant.
  • Screen Reader Focus treats web content as not applicable and only reports the DOM layer's hidden-element nodes.
  • Keyboard Focus uses focusability, tabindex and listeners, not order.

Fix: write the synthesized order into the snapshot's focusOrder (marked as derived), and wire the Tab-order probe into the host capture for Traversal Order Cycle.
