Causes were checked against the captured nodes, the rule code (ios_app_patcher master) and, where noted, on the iPad.

Summary

  • 2 gaps come from our WebView implementation, and both are fixable in the POC: the icon colour (verified on the device) and the missing visible-label signal for input fields.
  • 1 is a test-case problem: Text Truncation TC4 doesn't truncate at iPad width, and is detected on phones.
  • Everything else is parity: the existing iOS rule gives the same result on native screens. Each has a rule change that would help native and web alike (value-as-label for switches and editable fields, role and special-character vocabularies, state-indicator contrast, stricter overlap). Those belong in the rule engine, not the WebView POC.

The three rules in detail

Non-Text Element Color Contrast: TC2 icon colour (POC fix, verified)

Today the extractor takes getComputedStyle(svg).fill. An <svg> with no fill computes to black, so a #cfcfcf stroked icon is measured as #000000 against white, which passes. Fix: take the colour from the first shape the SVG actually paints, also inside ion-icon shadow roots:

const drawn = (svg) => {
  for (const s of svg.querySelectorAll('path,circle,ellipse,rect,line,polyline,polygon,use')) {
    const st = getComputedStyle(s);
    if (st.stroke !== 'none' && parseFloat(st.strokeWidth) > 0) return st.stroke;
    if (st.fill !== 'none' && !/url/.test(st.fill)) return st.fill;
  }
  return '';
};

Measured on the iPad: TC2 #000000 → #CFCFCF (1.6:1, FAIL as expected); TC5 #000000 → #5F6368 (6.1:1, still PASS). TC4 (state indicator) stays a rule-level gap.

Editable Element Accessibility Label: TC1, TC3 (parity)

BSRuleEditableElementContentLabel uses getBestAccessibilityLabelAndKey() (label → value → name). An unnamed field showing “John Appleseed”, or a contenteditable showing “Type a note…”, gets its text as the label. It is then sent to AI review instead of failing. A native text field with text gets the same treatment, so the POC keeps parity. Prod AI flagged TC1 for review (“label repeats the value”) and passed TC3.

Possible rule change (native and web): for editable fields, judge only the accessible name (label / name), never the value. TC1 and TC3 then fail deterministically.

Accessible Input Field Labels: TC3 (parity today, improvable for web)

The rule fails deterministically only when the placeholder is the label. A field named by aria-label with nothing visible goes to AI review, which passed it. Native gives the same result: an accessibilityLabel on a UITextField says nothing about visible text.

Web can do better, because the DOM says where the name came from. Add a nameSource property in the extractor (label · labelledby · aria-label · title · placeholder). When it is aria-label, title or placeholder, and no visible label sits next to the field, fail deterministically or pass the fact to the AI. Native screens are unaffected, because they never set it.
