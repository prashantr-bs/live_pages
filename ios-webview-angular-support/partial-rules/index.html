Partially supported rules: what's missing and what would fix it

Update (5 Oct): the 3 fixable gaps are fixed and verified on the iPad. Non-Text Contrast 2/4 → 3/4, Accessible Input Field Labels 2/3 → 3/3, Text Truncation 3/4 → 4/4. A full regression scan of all rule pages found 0 false positives; the POC total is now 61/127 (was 58). ios_app_patcher 5478df3 (PR #360), Rule Lab 9f73d1d. All other gaps are parity with the existing implementation and were left unchanged.

The 9 rules that were marked Partial on the summary, measured on the Angular + Ionic Rule Lab with the DOM-layer POC. For each missed test case: whether the cause is our WebView implementation (fixable in the POC), parity with the existing iOS rule (it behaves the same on native screens), or the test case itself. Causes were checked against the captured nodes, the rule code (ios_app_patcher master) and, where noted, on the iPad.

Summary

  • 2 gaps came from our WebView implementation, both now fixed: the icon colour and the missing visible-label signal for input fields.
  • 1 was a test-case problem, now fixed: Text Truncation TC4 didn't truncate at iPad width.
  • Everything else is parity with the existing implementation: the existing iOS rule gives the same result on native screens, so nothing was changed.

The three rules in detail

Non-Text Element Color Contrast: TC2 icon colour (fixed)

The extractor used to take getComputedStyle(svg).fill. An <svg> with no fill computes to black, so a #cfcfcf stroked icon is measured as #000000 against white, which passes. Fix (shipped in 5478df3): take the colour from the first shape the SVG actually paints, also inside ion-icon shadow roots:

const drawn = (svg) => {
  for (const s of svg.querySelectorAll('path,circle,ellipse,rect,line,polyline,polygon,use')) {
    const st = getComputedStyle(s);
    if (st.stroke !== 'none' && parseFloat(st.strokeWidth) > 0) return st.stroke;
    if (st.fill !== 'none' && !/url/.test(st.fill)) return st.fill;
  }
  return '';
};

Measured on the iPad: TC2 #000000 → #CFCFCF (1.6:1, FAIL as expected); TC5 #000000 → #5F6368 (6.1:1, still PASS). TC4 (state indicator) is parity with the existing implementation.

Editable Element Accessibility Label: TC1, TC3 (parity)

BSRuleEditableElementContentLabel uses getBestAccessibilityLabelAndKey() (label → value → name). An unnamed field showing “John Appleseed”, or a contenteditable showing “Type a note…”, gets its text as the label. It is then sent to AI review instead of failing. A native text field with text gets the same treatment, so the POC keeps parity. Prod AI flagged TC1 for review (“label repeats the value”) and passed TC3.

Accessible Input Field Labels: TC3 (fixed for web)

The rule failed deterministically only when the placeholder was the label. A field named by aria-label with nothing visible went to AI review, which passed it. Native gives the same result: an accessibilityLabel on a UITextField says nothing about visible text.

Fixed for web, because the DOM says where the name came from. The extractor emits webNameSource (labelledby · aria-label · label · title · placeholder) and webHasVisibleLabel. A field named by aria-label / title with no visible label now fails: “Input field of type TextField has no visible label (named only by aria-label)”. Like the existing placeholder failure, it still carries the check_input_field_purpose AI candidate. On the iPad: TC1–TC3 fail; the labelled fields TC5 and TC6 go to AI review as before (0 false positives). Native screens never set these keys and are unchanged.
