App Accessibility · WebView & Angular support · POC outcome · 30 Sep 2026

Can App Accessibility scan WebView content (e.g. Angular / Ionic apps)?

Today: barely. iOS reports nothing inside WebViews, and Android reports very little. With the POC (a change inside our iOS scanner), iOS finds most of the issues that can be found deterministically, with zero false alarms. Android can reach a similar level with a rule-engine change, because it already sees the content.

Why the two platforms fail differently

iOS: the scanner can't see inside the WebView

1Scanner runs inside the app and reads the screen's views
2A WebView's content lives in a separate Apple process. The scanner only sees an empty box.
3No elements, so no rule can check anything, and the screen looks "clean"
POCThe scanner now asks the WebView for its content (roles, names, sizes, colours) and feeds it to the existing rules

Android: the scanner sees it, then the rules skip it

1Scanner is an accessibility service; Chrome's WebView shares its content
2Buttons, links, fields and headings arrive with names and types
3Most rules only check elements marked "important", and Chrome never marks web elements that way, so they are skipped
FixMostly a rule-engine change (treat screen-reader-visible web elements as checkable) plus text-size estimation

What is supported, what isn't

iOS

TodayOnly the app-level orientation check works; everything inside a WebView is unscanned and reads as clean.

With POCLabels and names, touch targets, contrast (text and controls), truncation, text scaling (measured by actually enlarging the text), reflow and two-direction scrolling, keyboard reachability, and click-only elements with no role, including Ionic components inside shadow DOM.

Still limited

  • AI-judged rules need the AI step connected for web elements
  • reading / visual order rules need more work
  • a few iOS rules are narrower than their descriptions (e.g. "state in label" only checks "selected")
  • can't reach: Safari sheets (SFSafariViewController), canvas-drawn UIs, some cross-site iframes
  • adds ~1.2 s per scan, mostly the text-scaling check

Android

TodayTouch-target size / spacing and two-direction scrolling work on web content; contrast only reaches "needs review"; headings go to AI review.

Blocked~27 rules skip web elements because of the "important for accessibility" flag. Text-size rules have no font-size data from Chrome. Truncation always passes for web text.

Fix pathRule-engine change to accept screen-reader-visible web elements. Text size estimated from the screenshot (already done for Flutter). Let verified contrast fail.

Can't reachChrome Custom Tabs opened outside the app, canvas-drawn UIs.

Angular specifically

  • Angular + Ionic / Capacitor / Cordova (runs in a WebView): not scanned today on iOS and barely on Android. The POC covers it on iOS, including Ionic's shadow-DOM components.
  • NativeScript + Angular (renders native views): already supported like any native app.
  • Angular website inside a native app (checkout, help pages): same as the first row.
  • Angular's common defect, a clickable <div (click)>, is now detected on iOS: the POC notices click handlers.

Recommendation

1 · iOS: productionise the DOM layer

A change in the iOS scanner library (~500 lines, POC exists and runs on device) plus small matching rule updates on the server. The measured result is 0 → 58 of 127, with no false alarms. Next: connect AI review for web elements, gate the 1.2 s text-scaling check, and validate on customer hybrid apps.

2 · Android: unblock the rule engine

The content already reaches the scanner, so a rule-engine change unlocks most rules. We expect it to reach iOS-POC levels; that isn't measured yet, so the next step is a POC like iOS's.

Meanwhile: stop reporting "clean"

Mark screens with visible WebView content as "web content not fully assessed" on both platforms, so customers don't read silence as compliance.
